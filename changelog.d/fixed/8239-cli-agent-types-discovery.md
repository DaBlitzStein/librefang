`librefang agent new` no longer skips agent types that live only in `~/.librefang/agent-types/`.
`discover_template_dirs` in the CLI only ever scanned `workspaces/agents/` and `LIBREFANG_AGENTS_DIR`, both a directory per type, so it never looked at the flat `{name}.toml` store that has been the canonical destination for an operator-authored type since #7758 — and, via the registry sync fan-out, for every agent type a registry ships.
On a fresh installation, where `workspaces/agents/` is empty until an agent is actually deployed and the registry fan-out is the only source populating `agent-types/`, this was not "one template missing": `load_all_templates` returned nothing at all, and `librefang agent new` aborted with `agent-new-no-templates` before offering a single choice.
The kernel's own `agent_template_candidates` already searched the flat store first, so those types were immediately runnable from a workflow step and from the dashboard while invisible to the one command an operator is most likely to reach for.
`load_all_templates` now reads the flat store ahead of `workspaces/agents/`, matching the kernel's precedence so an `agent-types/` entry wins over a stale same-named workspace rather than being shadowed by it — the fan-out, the CRUD API, the spawn resolvers and the CLI now genuinely read and write the one shape a comment in `registry_sync.rs` already claimed they did.
`LIBREFANG_AGENTS_DIR` keeps beating both on-disk stores, because it is the one source the operator names on the invocation itself and the CLI documents it as an override; without that, a developer pointing it at a locally modified template would have silently got the registry's copy of the same name once `librefang init` populated `agent-types/`.
A flat-store file that cannot be read, whose stem the store's own writer would reject, or that a killed `agent_type_create` left zero-byte no longer consumes the type name — each of those used to hide a perfectly good `workspaces/agents/` template behind a row that could not be spawned.
