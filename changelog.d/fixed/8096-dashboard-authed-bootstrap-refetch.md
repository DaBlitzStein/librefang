The dashboard's user menu shows the account you actually logged in as, the machine's real hostname, and a Console link that follows the daemon's terminal policy, on a session that starts at the login dialog.
Two of those values were reachable before this fix only by accident of which endpoint was read: `GET /api/auth/dashboard-check` and `GET /api/version` are both unauthenticated and deliberately never echo the dashboard username or the hostname to an anonymous caller, so no amount of refetching them would have shown a real value. They now come from `GET /api/authz/whoami` and `GET /api/status`, both already fetched by the same bootstrap: `whoami` is authenticated outright, and `/api/status` is a dashboard-read route that requires auth whenever any is configured, which every deployment showing a login dialog is by definition.
The same swap applies to the change-credentials dialog, which prefilled its username fields from the unauthenticated endpoint and therefore opened blank for everyone.
On a deployment that runs no auth at all — `allow_no_auth`, a trusted loopback caller, or the master API key — `whoami` resolves the synthetic `root` identity, so the avatar there now reads `RO` where it used to show the generic placeholder icon.
That is intended: it names the credential the daemon is actually acting as, which a blank icon did not.
That bootstrap's authed half was also skipped while the user was still unauthenticated, and its only dependency was a stable Zustand setter, so it never ran a second time once the login succeeded: the avatar kept the generic placeholder icon and the Console link's visibility stayed at whatever the store already held rather than at what the daemon reports, for the rest of the session. A session restored from stored credentials was unaffected, because there the effect's own first run already finds the user authenticated.
The authed fetches now live in their own effect keyed on an auth epoch that the login callback bumps, covering every route through the dialog — username/password, TOTP, API key and passkey alike. That effect calls only the authed fetches, not the auth probe the mount effect owns, so a slow or failing re-check of the just-established session can't bounce the user back to the login dialog they already got past.
The mounted-guard the effect's continuations check is re-armed on setup rather than only cleared on teardown, so the fix holds under `vite dev` as well: `main.tsx` renders the app inside `<React.StrictMode>`, whose development mount → unmount → remount left a cleanup-only guard stuck at `false` for the rest of the session and returned every continuation early — reinstating, for anyone running the dev server, the placeholder avatar and hostname this change exists to remove.
