A turn that exhausts its iteration budget now delivers the best answer it has instead of returning nothing.
Previously, when the per-turn cap (`agent_max_iterations`, default 50) was reached, the loop returned `MaxIterationsExceeded`; the kernel's error arm only notified `alert_channels`, so the user saw silence indistinguishable from a hang. The loop now builds its response from the text accumulated across intermediate tool-use iterations — falling back to the same canned guard the normal end-turn path uses when there is none — pushes it as the assistant message, persists it (fork/incognito turns stay ephemeral), and returns `Ok` with a new `AgentLoopResult::hit_iteration_cap` flag. The kernel reads that flag and pushes a `max_iterations` operator notification, so the truncation is observable while the user still receives a partial answer. The streaming loop mirrors the same behaviour. (#8556) (@DaBlitzStein)
