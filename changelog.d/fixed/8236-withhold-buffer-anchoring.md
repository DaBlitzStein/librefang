The delta-withholding buffer that keeps raw `<function=...>` syntax off the wire was re-evaluated on every delta instead of being anchored to the first one, so a reply whose *later* delta happened to open with a known tool-call opener started withholding even though its earlier prose had already been sent.
  The stream then ended with something withheld, and the catch-up send re-emitted the whole reply — a client rendering deltas as they arrived saw the opening sentence twice, with the raw markup delivered after it regardless.
  The honest-reply guard could not rescue that case either, because a reply that opens with real prose is not a pure-markup reply and is returned unchanged by design.
  Withholding now only ever begins at the start of a reply, which is the only point at which the reply as a whole can still turn out to be markup end to end.
  Two related gaps close with it: the token-limit branch of the streaming loop never ran the honest-reply guard at all — it was added to the non-streaming loop only, so a `<function=...>` cut off mid-call by the token cap still reached every channel bridge and the dashboard verbatim, and that same branch never released what had been withheld, delivering no delta whatsoever for the turn.
  And a withheld delta used to count as content already on the wire, which suppressed the retry after an ordinary provider overload even though nothing had been emitted; the no-retry-after-content guard exists to avoid duplicating output the caller has seen, so it now tracks only bytes that were actually sent (#8236) (@DaBlitzStein)
