The system-channel `channel_send` instruction suppressed the tool for cron and autonomous turns as well as webui, but that was both false ("you are on the LibreFang web interface" is not true for a cron firing or a background tick) and a capability regression: cron and autonomous turns can still deliver media through `channel_send` when they name a real channel and recipient explicitly, since the #6117 cross-chat guard only fires when the turn's own channel matches the target.
The suppression now applies to webui only, and its wording states what actually happens — the browser renders a generated file only when the reply text embeds the `/api/uploads/...` URL the generating tool returned — rather than claiming media is attached to the response automatically, which nothing in the runtime does.
`channel_registry::is_system_channel` also kept a third hand-copied list of the cron/autonomous/webui literals behind a circular-dependency excuse that no longer held (`librefang-runtime` already depends on `librefang-channels`); it now delegates to `librefang_channels::types::is_reserved_system_channel`, which is drift-guarded against the kernel constants.
The prompt builder asks a different question from that one — whether anybody is waiting on the reply — so it now has its own `is_non_interactive_turn` over named constants instead of testing membership of the reserved list.
`webui` is reserved but a live browser session *is* waiting, so deriving the two from one list meant a future interactive surface added for `SessionId` reasons would silently start telling a real user their turn is a background one.
The two comparisons also normalise the same way now, so a `"WebUI"` no longer falls past the webui arm into the background-turn one. (#7995) (@DaBlitzStein)
