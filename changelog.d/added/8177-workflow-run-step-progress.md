Expose the live step progress of a workflow run — `current_step_index` and `total_steps` on the run plus each step's resolved `variables` snapshot — through `GET /api/workflows/runs/:id` and `GET /api/workflows/:id/runs`, and persist `total_steps` in SQLite (schema v56) so a run recovered after a daemon restart reports real progress instead of "step X of 0".
A finished run never reports a step it is no longer executing: the index is cleared at each terminal and pause transition, and the two endpoints read it through `WorkflowRun::live_step_index`, which answers `None` unless the run's state actually says it is running.
That second gate is there because `state` is assigned from dozens of separate branches of the execution loop, so the clear cannot be made to happen in one place — with the gate, a branch added later that forgets the clear still cannot make the dashboard render live progress on a run that has ended.
